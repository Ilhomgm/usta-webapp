# USTA — план реализации до 2030

Основа: MASTER CONCEPT 2030 пользователя. Это план, а не перечень готовых функций.
Принцип интерфейса: «Что вам нужно?» → задача → исполнитель → результат.
Этапы выполняются последовательно; календарные обещания до оценки команды не заданы.

| Этап | Объём | Критерий завершения |
|---|---|---|
| 1. Marketplace Core | Клиент, мастер, регистрация, категории, адрес, заказы, предложения, чат, отзывы, админка | Два разных пользователя проходят заказ от создания до завершения; данные сохраняются; чужие заказы недоступны |
| 2. Trust & Payments | Verified, цифровая смета, оплата, гарантия, спор, антифрод | Подтверждение сметы обязательно; повторы платёжных уведомлений не дублируют списание; спор и возврат имеют журнал |
| 3. AI | Диспетчер, фото, голос, подбор, перевод, ценовой диапазон | AI создаёт черновик с подтверждением пользователя; ошибки и низкая уверенность передаются человеку |
| 4. Professional Ecosystem | Pro, Teams, Academy, Jobs, Reputation Passport, финансовые партнёры | Репутация связана с подтверждёнными заказами; полномочия команды ограничены |
| 5. Commerce | Market, Supply, Delivery, Rent, Warehouse | Остатки, доставка, возврат и аренда имеют собственные состояния и учёт |
| 6. B2B | Business, Fleet, SLA, Service OS, API, White Label | Компании изолированы; бюджет и SLA контролируются; внешние API имеют ограниченные ключи |
| 7. Autonomous Platform | Autopilot, обслуживание по прогнозу, IoT, AI Call Center, Intelligence | Автоматические действия ограничены бюджетом/согласиями, отменяемы и полностью журналируются |

## Первый рабочий срез

1. Учётные записи и роли client/pro/admin; проверяемая сервером Telegram initData.
2. Постоянная база: users, professional_profiles, skills, addresses, orders, offers,
   order_events, messages, reviews; миграции и резервная копия.
3. Создание заказа из текста с категорией и адресом; список своих заказов.
4. Исполнитель видит подходящие заявки и отправляет цену/срок.
5. Клиент выбирает одно предложение; гонка выбора решается транзакцией.
6. Подтверждение выполнения, отзыв только после реального заказа.
7. Ручная модерация и журнал действий администратора.
8. RU/UZ как первый языковой срез; остальные языки концепции — расширение.

## Состояния заказа

created → analyzing → matching → offers → assigned → en_route → arrived →
diagnosis → estimate → awaiting_approval → in_progress → completed →
customer_review → payment → warranty → reviewed.

Отдельные ветви: cancelled, disputed. Этапы оплаты подключаются только с
реальным провайдером. Переходы проверяются на сервере; в order_events сохраняются
actor, время и причина. Изменение сметы требует нового подтверждения клиента.
Нельзя считать показ экрана подтверждением платежа или сохранения заказа.

## Что не входит в текущую настройку

Реальные платежи, escrow, проверка документов, AI-провайдер, SMS, production-база,
доставка и гарантии. Для них нужны отдельные реализации и подключения.
